# Sonar ROTMG — macOS source port (Apple Silicon)

This branch keeps the existing Java/Swing application and adds a macOS-specific native layer. It does not replace, modify, inject into, or automate the ROTMG Exalt game process. Packet capture remains passive.

## Target

- Apple Silicon (arm64)
- macOS 27 Golden Gate / 27.0.1
- JDK 17 for Gradle 7.6.4 builds; JDK 21 is preferred for the macOS GUI runtime
- Gradle wrapper 7.6.4

## Build and run from source

```bash
brew install openjdk@17 openjdk@21
git clone <your-sonar-fork-url>
cd sonar-rotmg

# Build/run using XML and sprite output generated by rotmg-network/exalt-extractor:
SONAR_EXALT_OUTPUT_DIR="$HOME/Library/Application Support/Sonar/exalt-extractor-output" \
  ./tools/macos/run-macos.sh
```

To build a `.app` and `.dmg` (run this on the Mac itself):

```bash
./tools/macos/build-macos.sh
```

Outputs are written to `build/macos/`. The app image and DMG are not code-signed or notarized; this is a developer build. Gatekeeper may require Control-click → Open.

## macOS privacy permissions

When launched from source, macOS may attribute access to Terminal. When launched as `Sonar.app`, grant the permissions to Sonar:

1. **Input Monitoring** — required for the global, listen-only Quartz event tap that observes key presses, wheel events, and minimap button clicks. Open System Settings → Privacy & Security → Input Monitoring, enable Sonar (or Terminal during source testing), then fully quit and reopen it.
2. **Screen & System Audio Recording** — required for CoreGraphics to read the Exalt window when locating the minimap. Sonar captures the game window only, not the whole desktop. Enable Sonar (or Terminal during source testing) under System Settings → Privacy & Security, then restart it.

The global event tap is listen-only and returns every event unchanged. It does not synthesize, block, or redirect game input.

## Packet capture permissions

Sonar uses the system `libpcap` library and BPF devices (`/dev/bpf*`), rather than Npcap. Do not run the GUI as `sudo`. If packet capture reports `Permission denied`, install the **ChmodBPF** package included with the official Wireshark macOS DMG. That installs a launch daemon which configures BPF device permissions and the `access_bpf` group; add your macOS user through the package's documented flow, then log out/in or reboot as directed by the installer. See the [Wireshark macOS installation guide](https://www.wireshark.org/docs/wsug_html_chunked/ChBuildInstallOSXInstall.html).

Check the current state with:

```bash
./tools/macos/diagnose-macos.sh
```

Homebrew installs `openjdk@17` as a keg-only JDK, so `/usr/libexec/java_home` may not list it until you create Homebrew's recommended JavaVirtualMachines symlink. The Sonar run, build, and diagnostic scripts now resolve the Homebrew JDK directly; a global symlink is not required.

The system libpcap can be loaded from Apple's dyld shared cache, so a plain filesystem existence check for `/usr/lib/libpcap.A.dylib` is not conclusive. The diagnostic script also checks the system `tcpdump` binary's linked libraries.

## ROTMG Exalt asset path and current macOS game data

The verified Exalt Client Mac Production build on the tested Apple Silicon setup is located at:

`~/.local/share/RealmOfTheMadGod/Production/RotMGExalt.app/Contents/Resources/Data/`

Sonar's `resources.assets` fallback detects this location first. The Steam folder `~/Library/Application Support/Steam/steamapps/common/Realm of the Mad God/RotMG Exalt Launcher.app` can be only a launcher/bootstrap installation and does not necessarily contain the live game-definition XML.

For the current Production build, use the cross-platform `rotmg-network/exalt-extractor` to resolve Unity's streamed resource data and export its XML, packet-name and sprite-sheet artifacts. The extractor is a separate prerequisite; Sonar imports its output rather than embedding a Python runtime. Run it against the installed client Data directory, then point Sonar to the output folder:

```bash
GAME_DATA="$HOME/.local/share/RealmOfTheMadGod/Production/RotMGExalt.app/Contents/Resources/Data"
python extractor.py --input "$GAME_DATA" --output "$HOME/Library/Application Support/Sonar/exalt-extractor-output"

SONAR_EXALT_OUTPUT_DIR="$HOME/Library/Application Support/Sonar/exalt-extractor-output" \
  ./tools/macos/run-macos.sh
```

Alternatively pass `-Dsonar.exalt.output=/path/to/extractor/output` when launching the JAR directly. Sonar also checks `SONAR_EXALT_OUTPUT_DIR` and the default `~/Library/Application Support/Sonar/exalt-extractor-output` folder. The expected extractor output contains `xml/`, `assets_manifest.json`, `spritesheets/spritesheet.json`, and the four PNG sheets (`groundTiles.png`, `characters.png`, `characters_masks.png`, `mapObjects.png`).

To have the source launcher rerun Exalt Extractor automatically on each start (recommended after a game patch), set `SONAR_EXALT_EXTRACTOR_DIR` to the cloned extractor repository. It uses that repository's `.venv/bin/python` by default; override it with `SONAR_EXALT_PYTHON` if needed. The game Data path can be overridden with `SONAR_EXALT_GAME_DATA`.

```bash
SONAR_EXALT_EXTRACTOR_DIR="$HOME/path/to/exalt-extractor" \
  ./tools/macos/run-macos.sh
```

Sonar parses only the XML files listed in the Exalt manifest's `objects` and `tiles` arrays, preserving manifest precedence. Do not parse every XML TextAsset: auxiliary files such as pet behaviours and title metadata can reuse numeric IDs and overwrite real object definitions. In the uploaded current client extraction, the manifest contains 159 object XML files and 59 ground XML files, yielding 36,397 Object records (36,230 distinct IDs after duplicate overrides) and 10,398 Ground records. The extracted `spritesheet.json` schema is supported by Sonar's JSON sprite metadata reader, while the four PNG atlases are imported into Sonar's sprite directory. Packet name files are retained as reference data; Sonar's Java packet decoders remain responsible for protocol handling.

When `SONAR_EXALT_OUTPUT_DIR` is provided, Sonar imports the external extraction into its per-user asset cache and then generates its own `ObjectID.list` and `TileID.list`. The original game installation and extractor output remain read-only. The cache signature includes the external output folder metadata and the asset format version so a changed extraction can trigger a refresh.

## macOS implementation notes

- **Packet capture:** Ardikars is directed to Apple’s system `/usr/lib/libpcap.A.dylib` on macOS; active IPv4 interfaces are selected and a missing/permission-denied capture device now produces actionable setup guidance rather than waiting indefinitely. BPF permissions are external OS setup.
- **Window tracking and minimap image:** CoreGraphics enumerates the Exalt window and captures that window only. The image path requires Screen Recording permission.
- **Overlay click-through and full-screen Spaces:** the port calls AppKit `NSWindow.setIgnoresMouseEvents:` and sets `CanJoinAllSpaces | FullScreenAuxiliary` for Sonar's Java overlay windows. It uses JDK AWT peer internals to obtain the native `NSWindow` pointer, hence the `--add-opens` flags in the launch scripts. JDK updates can change those internals; the app reports when click-through cannot be confirmed. Unity/Exalt full-screen behavior still needs testing on the target Mac.
- **Global input:** a Quartz session event tap observes input without modifying it. It needs Input Monitoring permission.
- **Game preferences:** macOS Unity preferences are read from likely Exalt `defaults` domains. If the bundle ID differs, Sonar falls back to Unity's default bindings.
- **Updates:** the existing updater only knows Windows release assets, so the macOS source port deliberately does not download or install Windows packages. Update manually from the fork until a signed macOS release workflow is added.
- **Recycle/clear history:** the macOS path asks Finder to move Sonar's history folders to Trash instead of using PowerShell's Recycle Bin API.

## Known verification limits

The source archive is patched in a Linux build environment. The user has verified that the prior macOS branch compiles with Gradle 7.6.4 on JDK 17. The new Exalt Extractor import path, manifest-ordered XML conversion, and JSON sprite-atlas path still require a build and runtime test on the target Mac. Native CoreGraphics/AppKit calls, privacy prompts, packet capture, and overlay click-through also require execution on that Mac. Treat this as a developer port, not a verified ready-to-play binary. Build and validate it on the target Mac, then share terminal output and `update/run.log` for any remaining native API differences.
